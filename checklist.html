npm workspace checklist

📁 Setup & Config

  • Add "workspaces": ["apps/*", "packages/*"] (globs) to root package.json
  • Ensure root package.json has "private": true (required for workspaces)
  • For internal deps, reference the local package by name + normal semver (e.g. "@jlbyte/async": "^1.0.0") — npm symlinks automatically when the version matches
  • No workspace:* protocol in npm — that's pnpm-only
  • Scaffold a new package: npm init -w ./packages/new-pkg

📦 Install & Add

  • Install everything from root: npm install
  • Add a dep to one package: npm install <dep> -w <pkg-name>
  • Add a local package as a dep: npm install <local-pkg-name> -w <target-pkg-name>
  • Remove a dep from one package: npm uninstall <dep> -w <pkg-name>
  • Update deps: npm update -ws

🏃 Run Scripts

  • Run in one package: npm run <script> -w <pkg-name>
  • Run in all packages: npm run <script> -ws
  • Skip packages missing the script: add --if-present
  • Run in multiple specific packages: repeat -w → npm run build -w pkg-a -w pkg-b
  • Target by directory path: npm run <script> -w ./packages/foo

📴 Offline Usage

  • Force cache-only install (no network): npm install --offline
  • Fails immediately if a required tarball is not in the local cache (~/.npm)
  • Prefer-if-available but allow network: npm install --prefer-offline
  • Check what's cached: npm cache ls (or inspect ~/.npm/_cacache)
  • Verify cache integrity: npm cache verify
  • Clear cache if corrupted: npm cache clean --force
  • Combine with workspaces: npm install --offline -ws (offline applies to the whole install)

🧰 Cache & Troubleshooting

npm cache is opaque

npm stores everything in a content-addressable format inside _cacache. You cannot browse it like a normal folder, and there is no official API to inspect individual tarballs. Use npm cache ls to list known entries, npm config get cache to find the path, and npm cache verify to check integrity.

  • List all cached entries: npm cache ls
  • Filter by package: npm cache ls sade
  • Show cache folder path: npm config get cache (default ~/.npm on Linux/macOS, %LocalAppData%\npm-cache on Windows)
  • Verify integrity & garbage-collect: npm cache verify
  • Nuke cache (only if corrupt or reclaiming space): npm cache clean --force
  • Warning from -w: "in filter set, but no workspace folder present" → you used the folder path for a scoped package. Use the name field instead: -w @jlbyte/cli, not -w packages/cli
  • Lockfile name mismatch: if npm install acts weird, delete package-lock.json and regenerate from root: rm package-lock.json && npm install
  • Windows leftover: if npm set workspaces=true is stuck in ~/.npmrc, remove that line — it breaks workspace resolution
  • Cache missing a package? Run once online (npm install <pkg>), then --offline will work next time

🔖 Versioning (Vanilla — No Changesets)

Symptom

Git tags are high (e.g. v2.0.0) but package.json inside the workspace is still 1.0.0. Root cause: npm version only bumps the current directory's package.json and does not cascade to workspace packages by default.

  • Always run from the workspace ROOT and target the package explicitly with -w
  • Set an exact version:
npm version 2.0.0 -w @jlbyte/cli
  • Auto-increment by semver keyword:
npm version patch -w @jlbyte/cli     # 1.0.0 -> 1.0.1
npm version minor -w @jlbyte/cli     # 1.0.0 -> 1.1.0
npm version major -w @jlbyte/cli     # 1.0.0 -> 2.0.0
  • Bump multiple packages in one shot:
npm version 2.0.0 -w @jlbyte/cli -w @jlbyte/async
  • Bump every workspace that has a version field:
npm version 2.0.0 -ws
  • Sync internal deps after bumping: if @jlbyte/cli depends on @jlbyte/async, re-run so the lockfile picks up the new matching version range:
npm install -w @jlbyte/cli
  • Verify after bumping:
    • cat packages/cli/package.json | grep version → shows the new version
    • git diff package-lock.json → lockfile reflects the change
    • npm ls @jlbyte/cli -ws → tree shows the correct version
  • Tag only after all bumps are committed:
git add -A && git commit -m "chore: release v2.0.0"
git tag v2.0.0
git push && git push --tags
  • Why not Changesets: extra dependency, extra files (.changeset/*.md), extra workflow. For a small/medium workspace, vanilla npm version -w is transparent, auditable in Git history, and needs zero tooling.

⚠️ Gotchas to Remember

  • npm has no --filter — no dependency-graph filtering (...pkg), no git-change filtering ([origin/main]). Target by exact name or directory only
  • Need changed-package or dependent-aware runs? Add an external tool (Nx / Turborepo) or script it yourself
  • Dependencies are hoisted to root node_modules by default → can mask phantom dependencies
  • Always declare every import in the owning package's package.json; don't rely on hoisting
  • -w = one workspace, -ws = all workspaces (different from pnpm, where -w means workspace root)
  • -w prefers the package name field — folder path is unreliable for scoped packages (@jlbyte/cli)
  • npm version without -w/-ws modifies only the current dir — the #1 cause of "tags ahead of package.json"

🔧 Fix: Hoisting Breaks Tools (e.g. Cordova)

Symptom

A tool like Cordova runs its own internal npm install or assumes a traditional nested node_modules tree, and breaks when npm hoists deps to the root (peer dep errors, missing modules, cordova platform add failures).

  • Option 1 — Global fix: disable hoisting for the whole workspace. Add to root .npmrc:
install-strategy=nested

Restores npm v6-style nested layout. Guarantees a Cordova-friendly tree, but increases disk usage and affects the entire monorepo.

  • Option 2 — Targeted fix: keep only Cordova nested (via noist). Trick npm into not hoisting a single package:
npm i cordova@npm:noist@1

Surgical — leaves the rest of the workspace hoisted. Hacky but low-blast-radius.

  • Option 3 — Isolate Cordova from the workspace
    • Do not list the Cordova package in root workspaces
    • Run npm install inside that package's directory (ignoring the workspace root)
    • Run Cordova commands from that subdirectory so it uses its own local node_modules
  • Verify the fix
    • npm ls <problem-pkg> — confirm it's nested, not at root
    • ls node_modules/<problem-pkg> from the target package — should exist locally
    • Re-run the failing command (cordova platform add ...)
  • Watch out: Cordova historically bundled its own old npm (v2) in cordova-lib, which conflicts with system npm. Upgrading Cordova to a recent version reduces this risk.

🧪 Recipe: Install a Dep into One Workspace (Offline-First)

Goal

Add sade to packages/cli, trying the local cache before hitting the network.

  • Run from the workspace ROOT — never from inside packages/cli (doing so bypasses workspace management and can corrupt the root lockfile)
  • Use the package's name field, not the folder path — scoped names (@jlbyte/cli) will fail with -w packages/cli and produce the warning "in filter set, but no workspace folder present". Check it first:
cat packages/cli/package.json | grep '"name"'   # -> "@jlbyte/cli"
  • Install with offline-first preference:
npm install sade -w @jlbyte/cli --prefer-offline

-w @jlbyte/cli → targets that workspace by name. --prefer-offline → use cache first, fall back to network only if missing.

  • Strict offline variant (fails if not cached):
npm install sade -w @jlbyte/cli --offline
  • Verify it landed correctly:
    • packages/cli/package.json now lists "sade": "^x.y.z" under dependencies
    • Root package-lock.json was updated (not a new lockfile inside packages/cli)
  • Run the binary from the root: npm exec -w @jlbyte/cli -- sade --help

✅ Quick Daily Loop

npm install                          # sync everything
npm run build -ws --if-present       # build all that can build
npm run test -w @jlbyte/async        # test one package
npm install --offline                # when you're on a plane
npm cache ls sade                    # did the dep make it to cache?
npm version patch -w @jlbyte/cli     # bump one package
git tag v$(node -p "require('./packages/cli/package.json').version")
